지금까지 LLM 어플리케이션의 가장 일반적인 요소를 살펴보았다 : 
- 프롬프트 기법 : [[Resources/books/Learning LangChain/1. LLM Fundamentals with LangChain\|Ch. 1]]
- RAG : [[Resources/books/Learning LangChain/2. Indexing Your Data (2) Vector Store\|Ch. 2]], [[Resources/books/Learning LangChain/3. Chatting with Your Data (1)  RAG\|Ch. 3]]
- Memory : [[Resources/books/Learning LangChain/4. Using LangGraph to Add Memory to Your Chatbot\|Ch. 4]]

이것을 어떻게 조합하느냐에 따라 LLM 어플리케이션은 다양하게 구현될 수 있다. 그 '조합 레시피'를 *인지 아키텍쳐*[^cognitive_architecture]라는 이름으로 정리한다.

설계는 *Agency*(자율성)과 *Reliability*(통제) 간의 트레이드오프로 시작된다. 자율적일수록 더 많은 일을 대신하지만, 잘못된 답변이나 판단을 할 가능성이 커지고, 통제할수록 안전하지만, LLM의 도움의 크기가 작아진다. 그러면 LLM은 어디까지 결정해야 할까? 이 책에서는 LLM의 자율성 스펙트럼을 세 단계로 소개하고 있다.
1) LLM이 한 단계의 출력을 결정하는가? (ex. 답장 초안 작성)
2) LLM이 다음 단계 선택을 결정하는가? (ex. archive vs reply vs review)
3) LLM이 가능한 행동 자체를 결정하는가? (ex. 내가 정의하지 않은 행동을 코드 생성으로 실행)

> 3)은 Agent Architecture(다음 장)와 연계된다.
#### Cognitive Architectures
##### 1. LLM Call : 단발 호출
한 번 호출해서 끝나는 설계이다. 요약이나 번역, 간단하게 생성하는 어플리케이션에서 사용할 수 있다. 단순해서 디버깅이 쉽고, 비용이나 지연을 예측하기 쉽다. 하지만 단순한 만큼 복잡한 작업을 할 수는 없다. [[Resources/books/Learning LangChain/4. Using LangGraph to Add Memory to Your Chatbot\|이전 장]]에서 실습해보았던 `chatbot` 노드 그래프가 하나의 예이다(실습은 생략한다).
##### 2. Chain : 정해진 순서의 여러 단계
LLM 호출을 여러 번 하되 순서가 고정된 파이프라인을 가지는 설계이다. 작은 Chain graph를 만들어보았다.

먼저 `State`, `Input`, `Output`을 정의하고, `builder`라는 `StateGraph` 객체를 만들고 LLM 모델을 2개 준비한다.
```python
class State(TypedDict):
    # 대화 히스토리 (누적 방식은 add_messages가 담당)
    messages: Annotated[list, add_messages]

    # input
    user_query: str

    # output
    sql_query: str
    sql_explanation: str

class Input(TypedDict):
    user_query: str

class Output(TypedDict):
    sql_query: str
    sql_explanation: str

builder = StateGraph(State, input=Input, output=Output)

model_low_temp = ChatOpenAI(temperature=0.1)
model_high_temp = ChatOpenAI(temperature=0.7)
```
`temperature`가 낮은 모델은 SQL 생성을 안정적으로 하고, `temperature`가 높은 모델은 설명을 자연스럽게 해줄 것이다.

다음으로, 첫 번째 노드인 `generate_sql`이다. 이 노드는 사용자의 질문을 받아 SQL을 생성하고, 대화 히스토리(`messages`)를 업데이트한다. 위에서 언급한 것처럼, `temperature`가 낮은 모델이 사용되었다.
```python
generate_prompt = SystemMessage(
    "You are a helpful data analyst who generates SQL queries for users based on their questions."
)

def generate_sql(state: State):
    user_message = HumanMessage(state["user_query"])
    messages = [generate_prompt, *state["messages"], user_message]
    res = model_low_temp.invoke(messages)

    return {
        "sql_query": res.content,            # 생성된 SQL을 state에 기록
        "messages": [user_message, res],     # 히스토리 업데이트(사용자 질문 + SQL 생성 결과)
    }
```

두 번째 노드인 `explain_sql`이다. 직전 단계에서 쌓인 메시지를 기반으로 SQL을 설명한다. 여기서는 자연스러운 설명을 위해 `temperature`가 높은 모델이 사용된다.
```python
explain_prompt = SystemMessage(
    "You are a helpful data analyst who explains SQL queries to users."
)

def explain_sql(state: State):
    messages = [explain_prompt, *state["messages"]]
    res = model_high_temp.invoke(messages)

    return {
        "sql_explanation": res.content,  # SQL 설명을 state에 기록
        "messages": [res],               # 히스토리 업데이트(설명 결과)
    }
```

`builder`로 두 노드를 추가하고, `START -> ... -> END` 순서로 edge를 연결한 뒤 graph를 실행 가능한 객체로 만든다.
```python
builder.add_node("generate_sql", generate_sql)
builder.add_node("explain_sql", explain_sql)

builder.add_edge(START, "generate_sql")
builder.add_edge("generate_sql", "explain_sql")
builder.add_edge("explain_sql", END)

graph = builder.compile()
```

실행 결과는 다음과 같다.
```python
result = graph.invoke({"user_query": "What is the total sales for each product?"})

print(result["sql_query"])

print(result["sql_explanation"])
# answer
To calculate the total sales for each product, you can use the following SQL query:

SELECT product_id, SUM(sales_amount) AS total_sales
FROM sales
GROUP BY product_id;

This query will sum up the sales_amount for each product_id in the sales table and display the total sales for each product.
Is there anything else you would like to know or any other questions you have about SQL queries?
```

그리고 `State`에 중간 결과를 쌓아두면, 스트리밍으로 각 단계가 뭘 했는지 관측할 수도 있다.

이 아키텍처는 작업의 순서가 정해져 있는 경우에 사용하면 좋다. '생성 -> 설명', '요약 -> 검증 질문 생성', '분류 -> 후처리' 등을 사용하는 어플리케이션에 적용할 수 있다.
##### 3. Router : 다음 단계 선택을 LLM이 한다.
여기서 자율성이 한 단계 올라간다. Chain과 다르게 '어떤 node로 이동할 지'를 LLM이 선택한다. 실습을 통해 아키텍처 구조를 살펴보자.

위의 실습과 초기 설정(`StateGraph`, LLM 모델 2개)은 유사하다. 다른 부분은, `State`에 `domain`이라는 state 필드가 "records"와 "insurance"만 가질 수 있도록 한 것과 embedding 모델이 하나 추가된 것이다.
```python
class State(TypedDict):
    ...
    # router 결과
    domain: Literal["records", "insurance"]
    ...

class Input(TypedDict):
    ...

class Output(TypedDict):
    ...

builder = StateGraph(State, input=Input, output=Output)

embeddings = OpenAIEmbeddings()
model_low_temp = ChatOpenAI(temperature=0.1)
model_high_temp = ChatOpenAI(temperature=0.7)
```

다음은 각 분기를 위한 Vector Store이다. 각 store는 retriever로 바꿔서 검색할 때 사용한다.
```python
medical_records_store = InMemoryVectorStore.from_documents([], embeddings)
medical_records_retriever = medical_records_store.as_retriever()

insurance_faqs_store = InMemoryVectorStore.from_documents([], embeddings)
insurance_faqs_retriever = insurance_faqs_store.as_retriever()
```

그리고 Router를 위한 프롬프트와 함께 Router node를 정의한다. 이 node는 사용자의 질문을 보고 `domain`을 결정하고, `messages`도 업데이트한다.
```python
router_prompt = SystemMessage(
    """You need to decide which domain to route the user query to.
domains:
- records: medical records (diagnosis, treatment, prescriptions)
- insurance: insurance policies/claims/coverage FAQs

Output only the domain name."""
)

def router_node(state: State):
    user_message = HumanMessage(state["user_query"])
    messages = [router_prompt, *state["messages"], user_message]
    res = model_low_temp.invoke(messages)

    return {
        "domain": res.content,              # "records" or "insurance"
        "messages": [user_message, res],    # 히스토리 업데이트
    }
```

분기를 만들어주는 edge를 정의한다. router가 만든 `state["domain"]` 값을 보고, 다음 노드를 선택하는 함수이다.
```python
def pick_retriever(state: State) -> Literal[
    "retrieve_medical_records",
    "retrieve_insurance_faqs"
]:
    if state["domain"] == "records":
        return "retrieve_medical_records"
    else:
        return "retrieve_insurance_faqs"
```

각 `domain`에 맞는 retriever를 호출해서 문서를 가져온다.
```python
def retrieve_medical_records(state: State):
    documents = medical_records_retriever.invoke(state["user_query"])
    return {"documents": documents}

def retrieve_insurance_faqs(state: State):
    documents = insurance_faqs_retriever.invoke(state["user_query"])
    return {"documents": documents}
```

그리고 검색된 문서를 바탕으로 답변을 생성하는 node이다. 이 부분에서도 `domain`에 따라 system 프롬프트를 다르게 주도록 설정한다.
```python
medical_records_prompt = SystemMessage("...")
insurance_faqs_prompt = SystemMessage("...")

def generate_answer(state: State):
    prompt = medical_records_prompt if state["domain"] == "records" else insurance_faqs_prompt

    messages = [
        prompt,
        *state["messages"],
        HumanMessage(f"Documents: {state['documents']}"),
    ]
    res = model_high_temp.invoke(messages)

    return {
        "answer": res.content,
        "messages": [res],   # 히스토리 업데이트
    }
```

node는 모두 정의했고, graph를 구성한다.![스크린샷 2026-01-30 오후 5.27.09.png|right|200](/img/user/Archive/attachments/%EC%8A%A4%ED%81%AC%EB%A6%B0%EC%83%B7%202026-01-30%20%EC%98%A4%ED%9B%84%205.27.09.png)
```python
builder.add_node("router", router_node)
builder.add_node("retrieve_medical_records", retrieve_medical_records)
builder.add_node("retrieve_insurance_faqs", retrieve_insurance_faqs)
builder.add_node("generate_answer", generate_answer)

builder.add_edge(START, "router")
builder.add_conditional_edges("router", pick_retriever)

builder.add_edge("retrieve_medical_records", "generate_answer")
builder.add_edge("retrieve_insurance_faqs", "generate_answer")

builder.add_edge("generate_answer", END)

graph = builder.compile()
```

입력 데이터에 대해 router node에서 어떤 `domain`을 선택했는지 확인해보았다.
```python
input_data = {"user_query": "Am I covered for COVID-19 treatment?"}

for chunk in graph.stream(input_data):
    if "router" in chunk:
        print(chunk["router"]["domain"])
        break
# answer
insurance
```

이 아키텍처의 핵심은 router를 이용해서 관련 인덱스만 태워서 정밀도를 높이는 것이다. 그래서 데이터나 도구, 정책이 여러 갈래로 나뉘는 제품의 경우에 적절한 아키텍처가 될 수 있다.

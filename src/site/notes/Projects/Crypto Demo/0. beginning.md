단순히 알고리즘을 공부하는 것도 재밌지만, 실제로 운영체제/라이브러리/언어 경계(FFI[^1])/DB/API 같은 현실적인 층위에서 어떤 문제가 생기는지 확인해보고 싶어서, 작은 데모 프로젝트를 하나 만들었다. 이름은 `crypto-demo`다. 이 프로젝트는 다음과 같은 질문에 대한 답을 구하기 위해 시작되었다.
- C로 제공되는 암호화 라이브러리(벤더 모듈 같은 것)를 Rust에서 어떻게 안전하게 호출할까?
- AEAD[^2]를 쓰면 '암호화' 외에 무엇이 더 보장되고, 무엇을 반드시 조심해야 할까?
- DB 컬럼에 암호문을 저장할 때는 어떤 형태로 저장해야 하고(예: nonce/tag 포함), 검색 같은 현실 문제는 왜 생길까?
- macOS에서 `.dylib` 링크/로딩 같은 OS 레벨 이슈는 어떻게 드러나고, 어떻게 정리할 수 있을까?

#### 프로젝트가 하는 일(2026-01-09 기준)
`crypto-demo`는 크게 두 덩어리로 나뉜다.
1. C provider (OpenSSL 기반)
	- OpenSSL을 사용해서 AES-GCM(AES-256 키) 방식으로 암/복호화를 수행한다.
	- API는 '벤더 모듈'처럼 보이도록 C ABI로 제공한다(핸들/에러코드 기반).
	- 결과는 보통의 AEAD 형태처럼 `ciphertext + nonce + tag`로 다룬다.
2. Rust server
	- Rust에서 C provider를 FFI로 호출한다.
	- unsafe 코드는 FFI 모듈에 최대한 가두고, 바깥에는 안전한 API로 노출하는 것을 목표로 한다.
	- REST API로 `/encrypt`, `/decrypt` 같은 엔드포인트를 제공하고,
	- SQLite에 '컬럼 암호화 저장' 형태로 데이터를 넣고 다시 꺼내는 흐름을 다룬다.

내가 이 프로젝트에서 확인하고 싶었던 것은 암호화 자체보다 경계에서 생기는 문제다. C ↔ Rust 경계에서는 포인터/길이/소유권/스레드 안전성이 핵심이 된다. API/DB로 들어가면 바이너리 데이터를 base64로 감싸야 하고, DB에 저장하려면 암호화된 정보 말고도 `nonce`/`tag` 같은 메타데이터가 항상 따라다닌다. 이것을 어떻게 구현해야 하는지, 그리고 생각해봐야 하는 것은 어떤 것들이 있는지 정리해보자.

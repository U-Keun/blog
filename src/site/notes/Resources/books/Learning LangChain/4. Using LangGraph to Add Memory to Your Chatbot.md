LLM은 기본적으로 상태를 기억하지 않는다. 모델은 호출될 때마다 이전의 대화가 없었던 것처럼 동작한다. 그래서 '대화형' 앱을 만들기 위해서는, 이전 대화나 문맥을 저장하고 다시 주입하는 '메모리 시스템'이 필요하다. 
#### 메모리 시스템
메모시 시스템은 다음과 같은 두 가지를 결정해야 한다.
- 상태(state)를 어디에/어떻게 저장할 지
- 저장된 상태를 다음 요청에서 어떻게 조회(query)해서 사용할 지

가장 단순한 방식은 대화 메시지 목록을 상태로 저장하고, 다음 호출 때 프롬프트에 그대로 붙이는 것이다. 이 방법은 쉽고 직관적이지만, 규모가 커지면[^1] 문제가 생긴다. 그리고 실제 운영 단계에서는 고려해야 할 것이 더 많다. 예를 들면, 
- 상호작용마다, 질문과 답이 모두 저장되어야 한다.
- 관계형 DB처럼, 신뢰할 수 있는 저장소를 사용해야 한다.
- 어떤 메시지를 어느 정도로 저장하고 사용할 지에 대한 정책이 필요하다.
- 대화 상태를 조회하거나 수정해야 할 수 있다.

LangGraph는 이것들을 위해 그래프 기반 상태 시스템을 제공한다.
#### LangGraph
LangGraph의 graph는 다음의 것들로 구성된다 : 
- State : 앱이 가지고 있는 '중앙 상태'. 모든 node가 공유한다.
- Node : 각 단계에서 수행하는 작업 단위로 볼 수 있다. 그냥 함수이고, 입력으로 현재 state를 받고 변경된 state를 반환한다.
- Edge : node 간 연결. '다음에 어디로 갈지'를 정한다.[^2]

##### `StateGraph` 생성
작은 graph를 생성해보자. `import` 구문은 생략한다.

먼저 `State`를 정의하고, `builder`라는 `StateGraph` 객채를 만든다.
```python
class State(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]

builder = StateGraph(State)
```

다음으로 OpenAI 모델을 하나 불러오고, `chatbot` 함수(node)를 정의한다.
```python
model = ChatOpenAI()  # 필요하면 ChatOpenAI(model="gpt-5-mini") 처럼 명시

def chatbot(state: State):
    answer = model.invoke(state["messages"]) # state["messages"] : 전체 메시지 히스토리
    return {"messages": [answer]}
```

`builder`로 `chatbot` node를 추가하고, `START` node[^3]와 `END` node[^3]를 `chatbot` node 앞 뒤로, edge를 이용해, 연결한다.
```python
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)

graph = builder.compile()
```
`builder.compile()`로 `graph`를 실행 가능한 객체로 만든다. 

실제로 실행해볼 수 있다.![langgraph_basic.png\|right\|100](/img/user/Archive/attachments/langgraph_basic.png)
```python
result = graph.invoke({"messages": [HumanMessage(content="hi!")]})
print(result["messages"][-1].content)
# answer
Hello! How can I assist you today?
```
> `graph.get_graph().draw_mermaid_png()`로 그래프를 시각화할 수도 있다 ->

#### 메모리 추가하기
graph를 `compile()`할 때 checkpointer를 붙이면, 매 실행마다 만들어지는 스냅샷을 checkpointer가 새로운 state로 저장한다.[^4] 그러면 다음 실행 때는 이전 state를 불러온 뒤, 새 입력을 합쳐서 시작하게 된다.

위의 예제에 이어서, `graph.compile()` 코드를 수정하고, 두 번의 실행으로 state가 저장되는지 확인해보았다.
```python
graph = builder.compile(checkpointer=MemorySaver())

thread1 = {"configurable": {"thread_id": "1"}}
result_1 = graph.invoke(
    {"messages": [HumanMessage(content="hi, my name is U-Keun!")]},
    thread1,
)
print("result_1:", result_1["messages"][-1].content)

result_2 = graph.invoke(
    {"messages": [HumanMessage(content="what is my name?")]},
    thread1,
)
print("result_2:", result_2["messages"][-1].content)
```
> `thread_id`는 대화(세션)별 Steate를 가리키는 인덱스로 보면 된다. 

추가로, `graph.get_state(thread)`/`graph.update_state(thread, content)`로 state를 조회하거나 수정할 수도 있다.
#### 히스토리 가공
대화가 길어지고 복잡해지면, 오히려 부정확한 응답이 나올 수 있다. 그것을 막기 위한 몇 가지 방법을 알아보자.
##### Trimming : 길이 제한
LLM이 받을 수 있는 토큰의 수는 한정되어 있기 때문에, 최근 대화를 중심으로 토큰 예산에 맞게 유지해야 한다. LangChain에서는 `trim_messages`로 다양한 전략을 제공한다 : 
- `max_tokens` : 남길 토큰 수
- `strategy="last"` : 최근부터 유지
- `include_system=True` : system 메시지는 유지
- `allow_partial=False` : 중간 잘림 없이 통째로 제거
- `start_on="human"` : AI 메시지만 남는 불균형 방지
##### Filtering : 필요한 메시지만 남기기
대화에서 메시지 타입, 이름, id가 다양해지면 정책적으로 걸러야 한다. LangChain의 `filter_messages`는 다음과 같은 일을 할 수 있다 : 
- `filter_messages(messages, include_types="human"` : human 메시지만 남기기
- `filter_messages(..., exlude_idx[..]` : 특정 id 제외하기
- `filter_messages(..., exclude_names=[...])` : 특정 name 제외하기
##### Merging : 연속된 동일 타입 메시지 병합하기
Anthropic 모델은 같은 타입 메시지가 연속적으로 입력되는 것을 제한해두었다. LangChain에서도 `merge_message_runs`로 연속적으로 들어오는 System/Human/AI 메시지를 병합한다.

> `filter | model`, `merger | model`과 같이 chain으로 합성해서 사용할 수 있다.

[^1]: 긴 대화, 다수 유저, 저장 정책, 내구성 등
[^2]: 조건부로도 사용될 수 있다.
[^3]: `StateGraph`와 함께 `langgraph.graph`에 정의되어 있다.
[^4]: 엄밀하게는, 여러 노드가 같은 super-step 안에서 병렬로 실행되고, 그 작업이 끝나면 state가 스냅샷으로 결정된다.

LLM을 프로젝트에 계속 붙여 쓰다 보면 어느 순간 이런 감각이 든다.
- 같은 배경 설명을 반복
- 답이 길어지고, 다시 좁히느라 왕복이 늘어남
결국 토큰은 '낭비 vs 절약'의 문제가 아니라, 결정에 쓰는 토큰과 왕복/설명에 새는 토큰이 섞이는 문제라고 생각했다. 내 목표는 간단했다:
> 토큰을 “결정과 산출물”에 쓰고, “반복 설명과 왕복”은 구조적으로 줄이기.

그때 눈에 들어온 게 Claude Code의 Agent Skills였다.
#### Agent Skills
###### 1) 반복 지침을 스킬로 이동하면, 대화가 짧아진다
원래는 매번 '출력 형식', '리뷰 기준', '디버깅 절차', '질문 개수 제한' 같은 걸 프롬프트에 붙이게 된다.  
이런 고정 규칙을 `SKILL.md`로 옮기면, 대화에서는 '이 스킬 적용해줘' 정도로 끝난다.
###### 2) 스킬은 필요할 때만 자세한 지침을 로드하는 구조가 된다
스킬은 보통 '이름/설명'만 가볍게 노출되고, 실제 본문 지침은 트리거될 때 로드되도록 설계된다.  
그래서 '항상 긴 시스템 프롬프트를 들고 있는 운영'보다 훨씬 비용이 절감되지 않을까..?
#### 적용 : Tickly 전용 스킬로 먼저 체감하기
나는 처음부터 범용 스킬로 가기보다, Tickly 프로젝트에서만 써 보면서 체감을 만들기로 했다. 핵심은 왕복을 줄이는 스킬을 먼저 만드는 것이다.
###### 스킬 1) Tickly 상태 스냅샷 5줄 (`tickly-state-5lines`)
매 작업 시작마다 “현재 상태”를 5줄로 고정 요약한다.
- Goal
- Now
- Constraints
- Today(딱 1개 작업)
- Next
이걸 고정하면 다음 대화부터는 '배경 설명'이 사라지고, 변경분만 공유하면 된다.
###### 스킬 2) Tickly 버그 트리아지 최소화 (`tickly-bug-triage-min`)
디버깅을 산문 대화로 하지 않고, 항상 이렇게 고정한다.
- 원인 후보 3개
- 후보별 검증 실험 1개씩
- 가장 가능성 높은 원인 1개
- 최소 수정안(diff)
- 질문 0~2개
이 루프의 장점은 긴 코드/로그 덤프 없이도 '실험으로 좁히는' 구조가 될 것이라고 생각했다.
#### Git 작업을 ‘개인 표준’ 스킬로 통일하기
Tickly에서 체감도 해보고 싶었지만, Git은 범용적으로 사용될 것 같아서 개인 표준 스킬로 등록해보고자 했다. 틀은 위의 것과 비슷하게 잡았다.
###### 목표: “안전한 동기화”를 고정 출력으로 만들기
내가 만들려는 Git 스킬은 이런 형태다.
- State 5줄 요약
- 추천 경로(Path A/B/C/D 중 1개)
- 실행 명령 1블록
- 주의 2개
- 질문 0~2개
이렇게 하면 Git 관련 질문도 '결정'과 '명령'으로 추려진다.
#### 설치 위치: 프로젝트 전용 vs 개인 재사용
나는 Git 스킬을 개인 표준으로 쓰기로 했기 때문에 **홈 디렉토리 아래 개인 스킬 위치**를 선택했다.
- Tickly 전용: `<repo>/.claude/skills/...`
- 개인 표준(Git): `~/.claude/skills/...`
Tickly는 실험/체감을 위해 프로젝트 내부에 두고, Git은 모든 프로젝트에 적용되도록 홈에 둔다.
#### Git 개인 표준 스킬 만들기: `git-sync-safe` (merge 기본)
##### `SKILL.md`
```markdown
---
name: git-sync-safe
description: GitHub push/pull/sync를 안전하게 진행한다. "pull", "push", "rebase", "ahead/behind", "diverged", "upstream", "fast-forward", "merge conflict" 상황에서 사용한다. 현재 상태를 짧게 요약하고(5줄), 추천 경로 1개와 실행 명령을 제시한다.
---

# Git Sync (Safe)

## 목표
- 실수(강제 푸시/잘못된 리베이스/충돌 확산)를 줄이며 빠르게 동기화한다.
- 답변은 짧고 실행 가능해야 한다.

## 기본 원칙 (MUST)
- 기본은 read-only 확인 후 진행한다: status/remote/branch/upstream/ahead-behind.
- 원격/히스토리를 바꾸는 명령(push, pull --rebase, merge, reset)은 "명령 제시"가 기본이다.
- 부족한 정보는 질문 0~2개까지만 한다.

## 출력 형식 (MUST)
1) State (exactly 5 lines)
- Branch:
- Remote:
- Upstream:
- Ahead/Behind:
- Working tree:

2) Recommended path (choose exactly 1)
- Path A: clean fast-forward pull / clean push
- Path B: diverged → merge (default)
- Path C: conflict triage
- Path D: uncommitted work first (stash/commit)

3) Commands (single code block)
4) Watch-outs (max 2 bullets)
5) Questions (0~2)

## 판단 로직
- working tree가 dirty면 Path D 우선
- behind만이면 Path A (fast-forward pull)
- ahead만이면 Path A (push)
- diverged면 Path B (merge로 고정해 제시)
- conflict가 감지되면 Path C
```
#### 메모
토큰 측정 로그가 없어서 지금 단계에서는 '얼마나 절약됐는지'를 단정하기 어렵다. 앞으로는 작업 하나를 단위로 스킬 사용 여부(A/B)를 기록하고, 완료까지의 왕복/시간/되돌림을 비교해 스킬이 실제로 효율을 만드는지 확인해보려 한다.

LLM을 프로젝트에 계속 붙여 쓰다 보면 어느 순간 이런 감각이 든다.
- 같은 배경 설명을 반복하게 된다
- 답이 길어지고, 다시 좁히느라 왕복이 늘어난다
결국 토큰은 ‘낭비 vs 절약’의 단순한 문제가 아니라, 결정에 쓰는 토큰과 왕복/설명에 새는 토큰이 섞이는 문제라고 생각했다.

내 목표는 간단했다.
> 토큰을 '결정과 산출물'에 쓰고, '반복 설명과 왕복'은 구조적으로 줄이기.

그때 눈에 들어온 게 Claude Code의 Agent Skills였다.
#### Agent Skills
##### 1) 반복 지침을 스킬로 이동하면, 대화가 짧아진다
원래는 매번 ‘출력 형식’, ‘리뷰 기준’, ‘디버깅 절차’, ‘질문 개수 제한’ 같은 걸 프롬프트에 붙이게 된다.  
이런 고정 규칙을 `SKILL.md`로 옮기면, 대화에서는 `/{skill 이름}` 정도로 시작할 수 있다.
##### 2) 스킬은 필요할 때만 자세한 지침을 로드하는 구조가 된다
스킬은 시작 시 name/description 같은 메타데이터만 먼저 로드되고, 실제 본문 지침(`SKILL.md`)은 스킬이 관련 있다고 판단될 때 읽히는 구조다.  
그래서 “항상 긴 시스템 프롬프트를 들고 있는 운영”보다, 왕복/반복 설명을 줄이는 방향으로 비용 구조가 유리해질 수 있다.
#### 적용: Tickly 전용 스킬로 먼저 체감하기

처음부터 범용 스킬로 가기보다, Tickly 프로젝트에서 먼저 써 보면서 체감을 만들기로 했다.  
핵심은 왕복을 줄이는 포맷을 먼저 고정하는 것이다.
##### 1) Tickly 상태 스냅샷 5줄 (`tickly-state-5lines`)
매 작업 시작마다 “현재 상태”를 5줄로 고정 요약한다.
- Goal
- Now
- Constraints
- Today(딱 1개 작업)
- Next
이걸 고정하면 다음 대화부터는 “배경 설명”이 사라지고, 변경분만 공유하면 된다.
```markdown
---
name: tickly-state-5lines
description: Tickly 작업 시작 시 현재 상태를 정확히 5줄로 요약한다.
---

# tickly-state-5lines

## Output (MUST)
Return exactly 5 lines in this order:
1) Goal:
2) Now:
3) Constraints:
4) Today:
5) Next:

## Rules
- Keep each line short.
- Do not add extra lines.
(… 생략)
```
##### 2) Tickly 버그 트리아지 최소화 (`tickly-bug-triage-min`)
디버깅을 산문 대화로 하지 않고, 아래 포맷으로 고정한다.
- 원인 후보 3개
- 후보별 검증 실험 1개씩
- 가장 가능성 높은 원인 1개
- 최소 수정안(diff)
- 질문 0~2개
```markdown
---
name: tickly-bug-triage-min
description: Tickly 버그 트리아지를 최소 포맷(후보3/실험3/원인1/diff/질문0~2)으로 수행한다.
---

# tickly-bug-triage-min

## Output (MUST)
1) Hypotheses (exactly 3)
2) Experiments (exactly 1 per hypothesis)
3) Most likely cause (exactly 1)
4) Minimal fix (diff-style, as small as possible)
5) Questions (0~2)

## Rules
- Prefer experiments over guessing.
(… 생략)
```

이 방식이 토큰을 직접 줄였는지는 아직 단정할 수 없다. 대신 내가 기대하는 변화는 분명하다. 배경 설명을 매번 새로 쓰지 않아도 되고, 문제를 좁히는 과정이 한 번에 같은 형태로 끝날 수 있다. 검증이 필요하겠지만, 일단 사용해보면서 체감해보자.
